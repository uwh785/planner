The application layer holds use cases and ports. It depends only on the domain.

- `auth`: session use cases and the authenticated HTTP client.
- `sync`: the sync engine (push then pull, backoff, status), the scheduler that decides when it runs and the coordinator that binds both to the signed-in user. See the Sync section of the root README.
- `planner`: what the screens use, built per signed-in container by `createPlanner`. `PlannerQueries`: `dashboard()` (the four counters, with the web's overdue rule through `TaskFilter.overdueAt`, and up to ten in-progress tasks), `tasks(scope)` (by list and by the web's status filter, split into open and completed), open counts per list, plain and `LiveQuery` versions that rerun on `container.dataChanges` (fires after local writes and applied pulls; `reload()` reruns for results that age with the clock). `ListUseCases` and `TaskUseCases` (validation is the domain's; edits include the estimated duration), `TaskTimerUseCases` (start and pause stamped with the moment of the tap, one write in flight per task and an 800 ms quiet period against double taps), `SubtaskUseCases` (add in creation order, check off, rename, delete; the backend's validation), `taskDetail(id)` / `watchTaskDetail(id)` (the task, its list and its subtasks), `CompletionWindow` (the five-second undo window; flushed on background, when a screen loses focus or goes away and before sign-out; `flush()` never rejects and reports the titles that could not be saved), `Notices` (the one line the screens say out loud, kept as a message key and params so it follows the language).
- `i18n`: the message catalogs (`messages/es.ts` is the source of the typed `MessageKey`, `messages/en.ts` must match it), `translate(locale, key, params)` (`{name}` placeholders; a `{one, other}` message picks its form from `{count}`), and `LocaleService` (the chosen language, Spanish by default, saved through the `LocaleStore` port; never rejects, so a broken store cannot block startup). Framework-free, so a desktop client can share it.

Timer transitions mirror the backend exactly (`domain/task.ts` `startTimer`, `pauseTimer`, `completeTimer`): start needs `pending` and sets `started_at`; pause needs `in_progress`, adds `at - started_at` (never negative) to `elapsed_ms`, clears the start and goes back to `pending`; complete needs `pending` or `in_progress`, adds the running segment and sets `completed_at`. Anything else rejects with `InvalidTransitionError` and changes nothing; so does an `at` that is not a positive integer. Each transition queues its own outbox entry `{entity: 'task', op: 'start' | 'pause' | 'complete', payload: {at}, change_id}` in the same transaction. They are not idempotent, so they are never coalesced: start, pause, start, complete are four entries kept in id order, behind the task's create (whose body always says `pending` with no start, so the server's create cannot pre-empt the transitions). Deleting the task drops its pending and parked transitions (and everything if it was never pushed). Push answers for all three: `applied`/`exists` clear the entry; `conflict` (the server task is in another state, for example already started or completed from another device) clears it and the pull of the same run brings the server's version, which wins; `not_found` retries five times and then parks as blocked; `invalid` (a bad `at`) parks as rejected. A pull never overwrites a task that has any entry, parked included. The backend has no reopen transition, so completion is final and the undo window exists: nothing is written until it elapses, and a process kill inside it loses the tick. Start and pause need no window.

Tags: the web app has no tag screen (only the plan usage), so M5d adds no tag use cases or UI; the repository keeps the link entities for sync.
